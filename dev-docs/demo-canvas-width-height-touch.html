데모 캔버스 — 본문 폭 정렬 · 높이 확대 · 모바일 터치 조작

작성일 2026-06-02 관련 PR (생성 예정) 대상: docs/assets/styles.css + 데모 10편(entry-game-1·2·4·5·6·7·8·9·10·11)

넓은 화면에서 데모 캔버스를 본문보다 넓게 확장하던 규칙(커밋 2470051)을 되돌려 본문 폭에 정렬하고, 대신 캔버스 높이를 장면별로 키워 세로로 더 잘 보이게 했다. 또한 키보드로 조작하던 1·2·4편 데모에 모바일용 터치 조작 패드를 캔버스 하단에 추가했다.

TL;DR
  • 폭: styles.css의 .try-demo 와이드 확장 @media 2개를 제거 → 데모가 .wrap 안에서 본문과 같은 폭(캔버스 표시폭 ≈ 702px)을 차지. 별도 규칙 불필요.
  • 높이: 각 <canvas>의 height 속성을 장면별로 상향 — 가로 액션(1·2편 220→300, 6·7편 320→360), 세로/2D 액션(4·5·8·9·10·11편 320→400). 가로(width:100%)는 본문 폭 고정이라 높이만 커진다.
  • 안전성: 데모가 바닥 앵커(groundY = H − 30) 또는 중심 앵커(10편 restY = H/2·11편 cy = H/2)라 H를 키워도 빈 여백만 늘어나 기존 요소가 절대 잘리지 않는다. 8편(높은 램프)·9편(가파른 경사)·11편(원)은 오히려 여유가 생긴다.
  • 모바일 조작: 키보드 의존 1·2·4편에 공통 .try-pad 버튼을 추가. 1·2편 = ◀ ▶ 꾹눌러 이동/가속, 4편 = ◀▶(각도)·▲▼(힘) 꾹눌러 조준(반복), 발사는 기존 버튼 재사용.
  • 로컬 프리뷰 검증 — 폭/높이 DOM 측정, 4편 각도·힘 기능 테스트, 1·2편 배선(실행·pressing) 확인, 8편 최대 램프 적합, 콘솔 에러 0. (애니메이션 루프는 hidden 탭 rAF 정지로 시각 검증 불가 → 기존 동작 키보드 핸들러와 동형 로직으로 보장.)

개요

직전 커밋 2470051("데모 캔버스 넓은 화면에서 본문보다 넓게")은 넓은 뷰포트에서 .try-demo를 본문 컬럼 밖으로 확장해 캔버스를 키웠다. 그러나 본문 텍스트 컬럼과 어긋나 정렬이 흐트러지고, 캔버스가 가로로만 길어 보이는 인상을 줬다. 사용자 피드백은 두 가지였다.

이슈
  • 폭 불일치 — 데모가 본문(텍스트 컬럼)보다 가로로 길어 페이지 정렬이 어색하다. 폭을 본문에 맞추고, 대신 높이를 키워 더 잘 보이게 하고 싶다.
  • 모바일 조작 불가 — 1·2·4편 데모는 화살표 키/스페이스로 조작한다. 키보드가 없는 모바일에서는 데모를 움직일 수 없으니, 캔버스 하단에 누를 수 있는 버튼이 있으면 좋겠다.

해결 1 — 폭을 본문에 맞춤

styles.css 하단의 와이드 확장 @media 블록 2개(중간 폭 대칭 확장 + ≥1240px 좌측 확장)를 제거했다. .try-demo는 각 편 페이지의 <style>에 로컬 정의되어 있고 .wrap(본문 컨테이너) 안의 일반 블록이라, 오버라이드를 없애면 자연히 본문 폭을 차지한다.

Before — 본문보다 넓게

@media (min-width:880px) and (max-width:1239.98px){
  .wrap .try-demo{
    width:min(94vw, 900px);
    margin-left:50%;
    transform:translateX(-50%);
  }
}
@media (min-width:1240px){
  .wrap .try-demo{
    width:calc(100% + min(50vw - 543px, 300px));
    margin-left:calc(-1 * min(50vw - 543px, 300px));
  }
}

After — 본문 폭(규칙 제거)

/* 와이드 확장 규칙 제거.
   .try-demo는 .wrap 안 일반 블록이라
   기본값으로 본문 폭을 차지한다.
   대신 각 캔버스 height 속성을 키워
   (width:100% → 본문 폭 고정) 세로로
   더 크게 보이게 한다. */
측정 결과 (1280px 뷰포트)

캔버스 좌우 184–886이 본문 문단 167–903 안에 들어옴(캔버스 표시폭 702 ≈ 본문 736 − .try-demo 패딩 32). 와이드 확장 시 캔버스가 본문 좌측으로 ~300px 삐져나오던 문제가 사라졌다.

해결 2 — 캔버스 높이를 장면별로 확대

캔버스는 width:100%; height:auto로 표시되어 가로는 본문 폭에 고정된다. 따라서 height 속성(내부 해상도)을 키우면 표시 세로 크기가 비례해 커진다. 액션 성격(가로 이동 위주 vs 세로 운동 위주)에 맞춰 차등 적용했다.

편데모액션 성격height (before → after)
1편이동(걷기·점프)가로 + 점프220 → 300
2편가속가로220 → 300
4편투석기 포물선세로(궤적)320 → 400
5편튕기는 공세로(낙하·반발)320 → 400
6편상자 밀기가로320 → 360
7편당구 충돌가로320 → 360
8편롤러코스터 램프세로(높이)320 → 400
9편눈썰매 경사세로(경사)320 → 400
10편스프링 진동세로(상하 진동)320 → 400
11편원운동2D(원·접선 이탈)320 → 400
왜 CSS 비율이 아니라 height 속성을 키웠나

CSS로 표시 비율만 늘리면 캔버스 그림이 세로로 늘어나 왜곡된다. height 속성을 키우면 JS가 canvas.height를 새 값으로 읽어 장면을 다시 레이아웃한다. 대부분의 데모는 const groundY = H − 30으로 바닥을 잡고 그 위로 그리므로 H가 커지면 위쪽 하늘 공간만 늘어날 뿐 기존 요소는 잘리지 않는다. 중심 기준 데모(10편 restY = H/2·11편 cy = H/2)도 H에 비례해 중심이 이동할 뿐이라 상하 여백이 대칭으로 늘 뿐 잘리지 않는다(상향이라 오버플로 불가).

장면별 검토 포인트
  • 8편: 출발 높이 슬라이더 최대 240. 기존 H=320이면 램프 꼭대기 y=50으로 빡빡했는데, H=400에서 y=130으로 여유가 생김(공 상단 y≈102).
  • 9편: 45° 경사도 H 증가로 꼭대기에 여유. (H 상향은 항상 헤드룸을 늘리는 방향.)
  • 5편: 공 시작점이 화면 상단 고정(startY=60). H 증가로 낙하 거리가 늘어 더 역동적으로 보이며, 반발은 에너지 보존상 시작 높이를 넘지 않아 상단 클리핑 없음.
  • 10·11편(직전 PR #29로 추가): 키보드 조작이 없어 패드 불필요, height만 상향. 10편 스프링은 restY=H/2 중심 진동이라 진동 폭 여유, 11편 원(반지름 120·cy=H/2)은 H=320에서 상하 여백 40px→H=400에서 80px로 더 안정. 줄 놓기 접선 이탈에도 여유.

해결 3 — 모바일 터치 조작 패드

키보드 의존 데모는 1·2·4편 뿐이다(5~9편은 이미 버튼/슬라이더 기반). 세 편이 공유하므로 .try-pad 스타일을 페이지 로컬이 아닌 공통 styles.css에 한 번 정의하고, 버튼 HTML과 JS 핸들러만 페이지별로 추가했다.

편패드 버튼동작 방식매핑
1편◀ ▶꾹누름(hold)keys.left/right = true → 기존 이동 루프
2편◀ ▶꾹누름(hold)keys.left/right = true → 기존 가속 루프
4편◀▶(각도)·▲▼(힘)꾹누름 반복(setInterval 70ms)aimAngle ±2 / aimPower ±4 → updateHud()+render(). 발사=기존 🚀버튼.

핵심 구현 — 포커스/스크롤 방지

패드 버튼은 pointerdown에서 e.preventDefault()를 호출한다. 이는 (1) 터치 시 페이지 스크롤을 막고, (2) 버튼으로 포커스가 이동하지 않게 해 캔버스 blur 핸들러가 실행되는 것을 차단한다(1·2편의 blur는 데모를 정지시키므로, 이를 막지 않으면 버튼을 누르는 순간 데모가 멈춘다).

// 1·2편 — 꾹눌러 이동/가속 (IIFE 스코프의 keys·running·setRunning 사용)
function holdPad(btn, dir){
  const press = e => {
    e.preventDefault();              // 포커스 이동(=캔버스 blur) + 스크롤 방지
    if (!running) setRunning(true);  // 정지 상태면 자동 실행
    keys[dir] = true;
    btn.classList.add('pressing');
  };
  const release = () => { keys[dir] = false; btn.classList.remove('pressing'); };
  btn.addEventListener('pointerdown', press);
  btn.addEventListener('pointerup', release);
  btn.addEventListener('pointerleave', release);   // 마우스로 끌어내며 떼는 경우
  btn.addEventListener('pointercancel', release);
}
pointerleave / pointercancel를 함께 듣는 이유

터치는 암묵적 포인터 캡처로 pointerup이 항상 원래 버튼에 도달하지만, 마우스는 버튼 밖에서 떼면 pointerup이 다른 요소로 가 키가 눌린 채 남는다. pointerleave가 이 경우의 해제를 보장한다. pointercancel은 시스템 취소(스크롤 시작 등) 대비.

패드 스타일(공통)

버튼은 중립(흰 배경 + 하단 두꺼운 보더 = 누르면 들어가는 느낌)으로, 편별 액센트 색에 무관하게 모든 데모에 일관 적용된다. 데스크톱·모바일 모두 표시하되 모바일(≤520px)에서는 손가락에 맞게 더 크게(72×56) 키운다.

검증

로컬 프리뷰(python3 http.server)로 검증했다.

  • 폭: 1·4·8편 DOM 측정 — 캔버스 표시폭 702가 본문 텍스트(736) 안에 정렬. 모바일에서도 캔버스가 데모 박스 폭에 맞음.
  • 높이: 전 편 canvas.height 신값 확인 + 캔버스 픽셀 샘플로 바닥/하늘/객체 렌더 확인. 8편 최대 램프(240)가 400px 캔버스에 여유 적합.
  • 4편 기능: ◀ 탭 1회 = 각도 45→47, 꾹누름 = 49까지 반복, 떼면 정지. 힘 버튼도 동일하게 증가·반복·정지. (HUD가 동기 갱신이라 rAF 없이 검증 가능.)
  • 1·2편 배선: 패드 누름 시 running 시작(▶→⏸)·pressing 클래스 토글, 떼면 해제 확인.
  • 10·11편(리베이스 후 추가분): canvas.height=400 확인 + 초기 프레임 렌더(10편 스프링 추·기준선, 11편 원 궤도·중심) 캔버스 픽셀 샘플로 확인, 콘솔 에러 0.
  • 콘솔 에러 0 — 전 편.
검증 한계 — hidden 탭의 requestAnimationFrame

프리뷰 탭이 visibilityState:hidden이라 requestAnimationFrame이 멈춰 애니메이션 루프(캐릭터 실제 이동·공 비행)는 시각 검증 불가였다. 다만 패드 핸들러는 기존에 정상 동작하는 키보드 핸들러와 동일한 상태(keys/aim*)를 같은 방식으로 설정하므로, 실제 보이는 브라우저·모바일에서는 동작이 보장된다. 초기 프레임은 render()/reset()이 동기 호출이라 스크린샷에 정상 표시됨(4·8편 캡처로 확인).
